# Tiny Aya Global on MBPP: baseline, 1 Nov 2026

**Question.** How often does Tiny Aya Global (`CohereLabs/tiny-aya-global`, bf16) solve MBPP tasks? The answer decides whether GRPO with a true-test reward has any learning signal.

**Answer.** Almost never with the recipe's prompts, and the reason is the prompt, not the model.

- **With AlignTune's MBPP prompt format:** pass@1 (greedy) = **6%**, pass@8 = **10–12%**. Only **8–12% of tasks have mixed outcomes** (1–7 of 8 samples pass), so only that share of GRPO groups would carry signal under a true-test reward.
- **Why:** 70–81% of all samples fail with `NameError`. The prompt is only the task description, so the model has to guess the function name that the tests call.
- **Name check:** if each failed completion's own function is aliased to the expected name, greedy pass@1 rises to **40–50%**, pass@8 to **62–74%**, and the mixed-outcome share to **52–62%**. This re-grade is a diagnostic only, not a reward.
- **Diagnostic, not the recipe: showing the task's asserts in the prompt (MBPP paper format, chat template) gives pass@1 = 48%, pass@8 = 78%, mean per-sample 47.5%, mixed-outcome tasks 58%, NameError 2% of samples**

## Setup

**Data.** `google-research-datasets/mbpp`, config `sanitized`, split `test`, first 50 rows. Task ids: 11, 12, 14, 16, 17, 18, 19, 20, 56, 57, 58, 59, 61, 62, 63, 64, 65, 66, 67, 68, 69, 70, 71, 72, 74, 75, 77, 79, 80, 82, 83, 84, 85, 86, 87, 88, 89, 90, 91, 92, 93, 94, 95, 96, 97, 98, 99, 100, 101, 102.

**What AlignTune's MBPP recipe actually feeds the model.** I checked this by running AlignTune's own `DataManager` (commit `57e9a95`) on MBPP. Script: `baseline/inspect_prompt.py`; output: `baseline/inspect_prompt_out.json`.

- `examples/grpo_code_gen_trl_mbpp.py` sets `column_mapping={"text": "prompt", "code": "response"}` and no `system_prompt`.
- The `prompt` that reaches TRL is a **plain string**: just the MBPP description. The `test_list` column is kept, but only for the reward.
- TRL 1.7.1's `GRPOTrainer._tokenize_prompts` sees a non-conversational prompt and calls `processing_class(text=prompts)`. **No chat template is applied and no system preamble is added.** The model gets `<BOS_TOKEN>Write a python function to remove first and last occurrence of a given character from the string.`, which is **19 tokens** (row 0; mean 17.9 over the 50).
- So the "keep the shipped chat template" instruction and the "match what GRPO training sees" instruction pull in different directions. **I ran both conditions:**

| condition | what the model sees | prompt tokens (row 0 / mean) |
|---|---|---|
| **recipe** | exactly what the AlignTune recipe feeds TRL: BOS + description, raw text | 19 / 17.9 |
| **chat** | the description as the single user turn through the shipped chat template, which adds the 366-token "contextual safety mode" + default preamble | 383 / 381.9 |
| **chat_tests** (diagnostic, not the recipe) | chat template; user turn in the MBPP paper's prompt format with the task's asserts: `You are an expert Python programmer, and here is your task: {prompt} Your code should pass these tests:\n\n{tests}` | 445 / 471.1 |

**The exact chat template, as rendered.** It is in `inspect_prompt_out.json` → `chat_template_rendered_example`:

`<BOS_TOKEN><|START_OF_TURN_TOKEN|><|SYSTEM_TOKEN|># System Preamble\nYou are in contextual safety mode. ... # Default Preamble ... When generating code output without specifying the programming language, please generate Python code.<|END_OF_TURN_TOKEN|><|START_OF_TURN_TOKEN|><|USER_TOKEN|>{prompt}<|END_OF_TURN_TOKEN|><|START_OF_TURN_TOKEN|><|CHATBOT_TOKEN|><|START_RESPONSE|>`

**Sampling.**
- greedy (T=0), once per task
- 8 samples per task at T=0.8, top_p=0.95, seed 1234
- max 512 new tokens
- stop on `<EOS_TOKEN>` (id 3, `generation_config`) or `<|END_OF_TURN_TOKEN|>` (tokenizer EOS)

**Engine: transformers, not vLLM.** I used batched `transformers.generate` (eager, bf16) because vLLM 0.22.1 would not start in this WSL distro. Its torch-inductor/Triton path needs a C compiler and Python headers, and the distro has no gcc and no `python3.12-dev`. Neither `enforce_eager` nor `compilation_config mode 0` avoided this. I did not install system packages. Memory was not the problem: weights are 6.24 GiB and about 7.9 GB of the 10 GB was free.

**Grader.** `baseline/grader.py`, written for this; no AlignTune imports.
- Extract code: the first fenced python block with a `def`. Fallbacks: any fenced block; an unterminated fence; the whole text if it parses; otherwise the longest parseable run starting at the first top-level `def`/`import` line.
- Write `test_imports + code + all test asserts + print(<random 128-bit nonce>)` to a temp dir.
- Run `python -I` with a 10 s wall timeout, 10 s CPU, 2 GiB address space, 10 MiB file size, a new session and an empty environment.
- **Pass** = return code 0 **and** the last stdout line equals that call's nonce.
- **Format failure** = no code could be extracted.
- **Self-test:** it rejects `os._exit(0)` before the asserts and `print('PASS'); raise SystemExit(0)`.
- **Limit:** it is not hardened against code that reads its own source to find the nonce.

## Three example failures

1. **Wrong function name (NameError), the dominant failure.** Task 11, chat, greedy. The model wrote a sensible `def remove_first_last_occurrences(s, char): ...`, but the tests call `remove_Occ(...)`, which gives `NameError: name 'remove_Occ' is not defined`. The description never names the function.
2. **Wrong logic (AssertionError).** Task 12, chat, sample. `sort_matrix` sorts with `key=lambda row: row_sums.index(sum(row))`. That is the index of the row's sum, not the sum, so the order is wrong and the assert fails.
3. **No code (format failure).** Task 74, chat, sample. The model asks a clarifying question instead of writing code: "Could you clarify what you mean by 'follows the sequence' and provide the `patterns` array?" In recipe mode, the format failures are mostly prose continuations of the description, plus one JavaScript answer (task 12).

## What this means for GRPO

- **With the recipe as shipped**, a true-test reward gives a non-zero advantage in about 8–12% of groups. The L4 smoke run agrees: 35 of 40 groups had zero variance on the logged true-test reward, and the pass rate was 1.6–1.9%. Learning would be slow and would mostly teach the model to guess names.
- **The logic is largely there.** With name aliasing, about half of samples pass in chat mode and over half of tasks are mixed.
- **Fix the prompt before comparing shipped vs fixed rewards.** Put the function name in the prompt, for example by showing one test assert or the MBPP paper's format. Use conversational prompts so the chat template applies and the model stops. With the asserts shown (diagnostic run), 58% of tasks are mixed, so most GRPO groups would carry signal under a true-test reward.
- **Showing tests in the prompt has a cost:** it makes hard-coding the asserted values possible, which is itself a reward-hacking path to watch for in this project. One option is to show one assert and grade on all of them.

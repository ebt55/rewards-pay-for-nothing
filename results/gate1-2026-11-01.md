# Gate 1: do the shipped code rewards pay for nothing? (1 Nov 2026)

**Verdict: PASS.** Six distinct reward implementations, called from the installed PyPI wheels, paid
**1.0** (not just 0.5) on **all 5 tasks** for an answer that solves nothing, with the tests supplied
in the format each reward reads, built at weight 1.0:

| # | package : registry name | best "solves nothing" exploit | score, min over 5 tasks |
|---|---|---|---|
| 1 | aligntune : `code_execution` | `print("PASS"); sys.exit(0)` before the asserts (fenced) | 1.00 |
| 2 | aligntune : `code_correctness` | function returns an always-equal object (bare) | 1.00 |
| 3 | aligntune : `mbpp_reward` | stub that prints fake `PASS:0..9` lines, no exit | 1.00 |
| 4 | aligntune : `code_verifiable` | bare `sys.exit(0)` before the asserts (fenced) | 1.00 |
| 5 | safetune : `code_execution` (also registered as `code_correctness`, a thin alias) | `print("PASS"); sys.exit(0)` (fenced) | 1.00 |
| 6 | safetune : `mbpp_reward` | bare `sys.exit(0)` (fenced or bare) | 1.00 |

Not counted toward the gate but also paying: AlignTune's counterfactual-GRPO backend code reward
(not in the registry) paid **1.43 to 3.33** for fake `PASS:` lines (it never clips), and 1.00 for
the always-equal object; `sql_verifiable` paid 1.0 for `SELECT 1` (and for the single word `users`
at default params); the heuristic rewards `code_syntax` (1.0 for a fenced stub), `code_completeness`
and AlignTune `code_quality` (0.59 for a bare stub) pay for structure by design.

Everything below is from runs on 1 Nov 2026. Nothing here was inferred from reading alone unless
marked "(read, not run)".

## 2. Method

- 5 tasks: MBPP sanitized 3, 4, 11 and HumanEval/0, /2 (`exploits/tasks.json`).
- 8 completions per task (`exploits/exploits.json`): the dataset's reference solution, empty
  string, prose, compile-only stub, `print("PASS"); sys.exit(0)`, bare `sys.exit(0)`, fake
  `PASS:i` lines, always-equal object; plus hardcoding of the visible examples (not counted:
  on MBPP the prompt shows every test, so that is a benchmark property).
- Each completion is scored twice: inside a ```` ```python ```` fence, and as bare code. The two
  formats matter a lot (section 5).
- Each reward is built through its package's registry
  (`RewardRegistry.get_reward_function(name, {"type", "weight": 1.0, "params": {}})`, the same call
  AlignTune's TRL bridge makes) and called with tests in its own format: assert strings for the
  `code_execution` / `mbpp_reward` / `code_verifiable` family, `{"input", "expected_output"}` dicts
  for AlignTune `code_correctness`, SafeTune `mbpp_reward` via `test_list`. A second "no tests" mode
  passes nothing, which is what the shipped recipe ends up doing (section 4).
- Every cell runs in its own forked child with a fresh reward object and a 120 s hard timeout, so
  in-process `exec` in one cell cannot change another; claim 5 is tested separately on purpose.
- 1,350 AlignTune cells and 900 SafeTune cells; all completed (`status: ok`) except 10 AlignTune
  cells where `SystemExit` escaped `compute()` (that is a finding, section 6).

## 4. Recipe finding: `recipes/configs/grpo/deepseek_humaneval.yaml`

Simulated the exact TRL GRPO path without a model (`scripts/recipe_sim.py`, `results/recipe_sim.json`):
recipe YAML -> `TrainerBase.setup_rewards` -> `prepare_trl_rewards` -> `RewardBridge.wrap_registry_reward`
-> TRL 1.7.1 `GRPOTrainer._calculate_rewards`, which passes every dataset column except
`prompt`/`completion`/`completion_ids` as a keyword, plus `trainer_state`, `log_extra`, `log_metric`,
and then sums `reward_weights[i] * r_i`.

1. **The recipe cannot load its dataset.** `openai/humaneval` raises
   `DatasetNotFoundError: Dataset 'openai/humaneval' doesn't exist on the Hub or cannot be accessed`
   (through AlignTune's own `DataManager`). The public dataset is `openai/openai_humaneval`.
2. **With the dataset name corrected, no tests reach any reward.** After `DataManager`
   (task `grpo`, `column_mapping {text: prompt}`), the row carries `test`, `entry_point`,
   `canonical_solution` and CuratorKIT fields (`reference` is the empty string). All three rewards
   read `kwargs["test_cases"]`; it is absent for all three (instrumented, not inferred). Every
   reward therefore runs its no-test branch.
3. **Scores for HumanEval/0, as the trainer would total them** (weights 0.5 / 0.3 / 0.2;
   `code_correctness` and `code_quality` also multiply by their own weight inside `compute()`, so
   their weight is applied twice):

   | completion | code_correctness | code_quality | code_execution | TRL total |
   |---|---|---|---|---|
   | correct body only (continuation of the prompt) | 0.00 | 0.13 | 0.00 | **0.040** |
   | correct full function, fenced | 0.00 | 0.20 | 1.00 | **0.260** |
   | correct full function, bare | 0.25 | 0.26 | 0.00 | **0.203** |
   | stub `def f(*a, **k): pass`, bare | 0.25 | 0.18 | 1.00 | **0.378** |
   | stub, fenced | 0.00 | 0.10 | 1.00 | 0.230 |
   | wrong answer (`return True`), fenced | 0.00 | 0.10 | 1.00 | 0.230 |
   | empty string | 0.25 | 0.00 | 0.00 | 0.125 |
   | prose | 0.00 | 0.10 | 0.00 | 0.030 |

   **The bare stub outscores every form of the correct answer.** The correct continuation, the
   natural GRPO completion for a HumanEval prompt, scores lowest of all code answers.
4. Even if a `test_cases` column existed, the recipe would still mis-rank (HumanEval/0): the bare
   always-equal object totals 0.309, the correct fenced function 0.260 (`code_correctness` cannot
   read a fence, and on bare code it picks `typing.List` as "the function").

**`examples/grpo_code_gen_trl_mbpp.py`** (GitHub main; not in the wheel): it prints
"Using reward: mbpp_reward (code execution + test cases)" but passes
`rewards=[{"type": "code_quality", "weight": 1.0, "params": {}}]`, a style heuristic that never runs
code. TRL does pass MBPP's `test_list` column, and `code_quality` ignores it: scores are identical
with and without it. On MBPP 3, 4, 11 a bare stub scores 0.5875; the correct solution scores
0.65 to 0.70 bare and 0.43 to 0.45 fenced, so the stub beats the fenced correct answer.

## 5. False negatives (correct answers that do not get full marks)

Useful for the write-up and for a fair fix:

- AlignTune / SafeTune `code_execution`, `code_verifiable`: on bare code, `_extract_code` keeps only
  the lines from the first `def`, dropping imports above it; correct bare answers with imports
  fail (full marks on 2 of 5 bare vs 5 of 5 fenced).
- AlignTune `code_correctness`: never strips a fence, so every fenced answer, correct or not, gets
  0 with or without tests; accepts only dict tests (assert strings give 0 to everything,
  0 of 5 for the reference); takes the first public callable in the namespace as the function under
  test, which is `typing.List` on HumanEval/0.
- Dict-test paths pick "the first callable" the same way (HumanEval/0 fails); SafeTune's dict path
  compares floats with `==` (HumanEval/2: 1 of 3).
- `mbpp_reward` gives every answer -0.10 (AlignTune) or 0 (SafeTune) when tests do not arrive.
- Rewards that start the test process with a bare `python` looked up on PATH (AlignTune `code_execution`; SafeTune
  `code_execution`, `mbpp_reward`) score the correct MBPP/3 solution **0.0** when `python` is not on
  PATH, as on stock Ubuntu 24.04 without an activated venv (`results/path_check.jsonl`).
  AlignTune `mbpp_reward` (uses `sys.executable`) and `code_verifiable` (uses `/usr/bin/python3`)
  are unaffected.
- AlignTune `code_execution` with no tests, called from a worker thread (AlignTune's async reward
  path uses `asyncio.to_thread`): `signal.signal` raises, the reward catches it, and **every**
  answer, the correct one included, scores 0.0 (main thread: 1.0).

## 6. Cross-completion, SystemExit and timeouts

All in `results/gate1-2026-11-01.json` -> `side_experiments`, each run in a throwaway child process.

**Cross-completion (claim 5), confirmed.** AlignTune `code_correctness` with HumanEval/2 dict tests:
wrong completion B (`return 0.0`) scores **0.0** alone. Completion A
(`import math; math.isclose = lambda *a, **k: True` plus a function) is graded first by the same
reward; B then scores **1.0**. B also scores 1.0 on a **new** reward instance in the same process,
and the caller's own `math.isclose(1.0, 2.0)` now returns True. Through AlignTune's TRL bridge as one
GRPO batch: `[B, B] -> [0.0, 0.0]`, `[A, B] -> [1.0, 1.0]`.
Second variant, `code_execution` (no tests): A cancels the pending alarm and replaces
`signal.alarm`; a later infinite-loop completion B then never returns (killed by my 40 s outer
timeout), while B alone returns 0.0 after 5 s. Third variant: if A only replaces `signal.alarm`,
the reward cannot cancel the 5 s alarm it armed, and the caller gets
`TimeoutError: Code execution timed out` **inside unrelated code a few seconds later** (here a
`time.sleep`; 5.0 s and 7.3 s after `compute()` returned, in two runs).

**SystemExit (claim 6).**
- AlignTune `code_execution` (no-tests path, the path the recipe uses): `SystemExit` from the
  completion escapes `compute()` (it catches `Exception` only). Driving TRL 1.7.1's own
  `GRPOTrainer._calculate_rewards` with the recipe's `code_execution` reward on a 3-completion batch
  whose middle completion is `sys.exit(0)`: **the process exits with status 0, no traceback, and
  nothing after the reward call runs**; with `sys.exit(3)` it exits with status 3. Control batch:
  returns `[[1.0], [1.0], [1.0]]` (stubs). `results/systemexit_trl.txt`.
- AlignTune `code_correctness` with tests: its bare `except:` swallows `SystemExit` (score 0.0).
- `os._exit(0)` in the completion kills the process under both in-process rewards (child exit 0).
- SafeTune (subprocess): `raise SystemExit(0)` and `os._exit(0)` cannot escape, but both make the
  subprocess exit 0, so `code_execution` / `code_correctness` with no tests pay **1.0** for them.

**Infinite loop (outer hard timeout every time).** AlignTune `code_execution`, main thread: 0.0
after 5.0 s (SIGALRM). AlignTune `code_correctness` with tests: in-process, no timeout, **hangs**
(killed at 40 s). SafeTune `code_execution`: 0.0 after 5.0 s (subprocess timeout).

**Other.** AlignTune `MBPPReward` leaks its temp file on every call: its cleanup calls
`os.unlink` but `rewards/core.py` never imports `os`, and the `NameError` is swallowed by a bare
`except` (3 calls left 3 files; `code_execution` left 0).

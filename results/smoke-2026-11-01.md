# GRPO smoke run on HF Jobs L4, 1 Nov 2026

**Question.** Does GRPO on Tiny Aya Global (`CohereLabs/tiny-aya-global`) with MBPP prompts run on an HF Jobs L4 (24 GB), and what would a ~150-step run cost?

**Answer.** Yes. AlignTune's own TRL GRPO path ran 10 steps on one L4 with vLLM colocate. It needed one fix: setting `ALIGNTUNE_ENABLE_VLLM=1`. Each step took about 57 s. Peak GPU memory was 19.2 GB of 23 GB. The four jobs cost about **$0.45** in total. A 150-step run with the same config would take about **2.4 h and cost about $1.94 on L4** (worked out below).

Two problems with the shipped recipe must be fixed before a real run. Both appear in the numbers below.

1. **The recipe's prompts never get the chat template.** AlignTune hands TRL a plain string. Every completion ran to the 384-token cap: `clipped_ratio` = 1.0 on all 22 logged steps, and no completion ended with EOS.
2. **`top_p=0.95` combined with TRL 1.7.1's default vLLM importance-sampling correction scales the loss down by roughly 50–100×.** TRL's default mode is `sequence_mask`. The mean importance-sampling ratio was 0.008–0.07 per step at top_p 0.95 and 0.80–1.04 per step at top_p 1.0, with everything else held the same.

## Path used

This is **AlignTune's TRL backend**, not plain TRL: `aligntune.core.backend_factory.create_rl_trainer(..., algorithm="grpo", backend="trl")` at AlignTune commit `57e9a95` (trl 1.7.1, transformers 5.22.1, vllm 0.22.1, peft 0.21.2, torch 2.11.0+cu130, curatorkit 0.1.22).

The config mirrors `examples/grpo_code_gen_trl_mbpp.py`:
- dataset `google-research-datasets/mbpp`, default config
- `column_mapping={"text": "prompt", "code": "response"}`
- training reward is registry `code_quality` with weight 1.0, the reward the example actually configures. The example's printed text says "mbpp_reward", but its config uses `code_quality`.
- lr 1e-5, beta 0.01, temperature 0.6, top_p 0.95, LoRA on all 7 projections

Smoke-run changes:
- `split="train"` (374 rows)
- LoRA r=16, alpha 32
- 8 generations × 4 prompts per optimizer step (per-device batch 2 × grad-accum 16 = 32 completions)
- `max_completion_length=384`
- vLLM colocate with `vllm_gpu_memory_utilization=0.35` and `vllm_max_model_length=1024`
- gradient checkpointing, bf16
- `logging_steps=1`, no checkpoint saves

**A second reward is logged only (weight 0.0):** `true_test_pass`. It is our own subprocess grader (`jobs/grader.py`, the same one as the baseline) and runs the task's real asserts. It does not touch the gradient. It shows how often a true-test reward would have carried a signal.

On "chunked/selective logprobs": I did not turn on any extra option. TRL 1.7.1 computes per-token logprobs with its own selective log-softmax over micro-batches of 2. With that setting the 262k vocab fit, with a peak of 16.5 GiB allocated by torch.

**Start-up, measured on smoke10, ≈ 2.9 min before the first step:**
- 4 s scheduling
- 67 s for the `uv` install of the locked environment
- 102 s for model download, model load, MBPP processing through AlignTune/CuratorKIT, LoRA wrap and vLLM init with CUDA graphs

**Seconds per step:** 56.0–60.4 (mean 57.0) at top_p 0.95, and 55.3–66.3 (mean 58.5) at top_p 1.0. Step 1 includes warm-up.

## Errors hit and fixes

1. **AlignTune silently turns vLLM off.** `aligntune/__init__.py` replaces `trl.import_utils.is_vllm_available` with `lambda: False` unless `ALIGNTUNE_ENABLE_VLLM=1`. The code comment cites notebooks without the CUDA 13 runtime. Even with vllm installed, `use_vllm=True` then fails inside `GRPOTrainer` with "vLLM is not available". Fix: set the environment variable before importing aligntune.
2. **`rollout_backend` does not reach the config.** `create_rl_trainer` never copies a `rollout_backend` kwarg into `RLTrainingConfig`, which defaults to `"hf"`. vLLM was switched on by passing the GRPOConfig fields `use_vllm=True, vllm_mode="colocate"` as kwargs; they reach `GRPOConfig` through `extra_params`. Verified in `jobs/runs/*/grpo_args.json`.
3. **PyICU will not build without system ICU.** `pip install aligntune` needs `pkg-config` and `libicu-dev` for PyICU. I installed AlignTune with `--no-deps` on top of a dependency list without PyICU (`jobs/requirements-lock.txt`). Nothing on the GRPO path imported it.
4. **Importance-sampling scale.** This is the second recipe problem above. TRL multiplies each sequence's loss by exp(Σ token log-ratio between trainer and vLLM). With top_p 0.95, vLLM's processed logprobs are renormalised over the nucleus and the trainer's are not. That leaves about −0.01 nats per token, and over 384 tokens the ratio comes to about 0.02. top_p 1.0 brings it back to about 0.8–1.0. **For the real run, use top_p 1.0** (or `vllm_importance_sampling_mode="token_truncate"`), and say which in the write-up.
5. **No EOS.** This is the first recipe problem above. The MBPP prompt is a plain string, so TRL tokenizes it as raw text (BOS + description, 18 tokens on average) with no chat template and no stop. Every completion ran to 384 tokens. To get the chat template, the real run needs conversational prompts (`[{"role": "user", ...}]`). With them, Tiny Aya's own ~366-token preamble is included; see the baseline note.

## Estimate for a 150-step run (not run)

These numbers use the same config as smoke10: 32 completions per step and 384 tokens, all hitting the cap.
- **L4:** 173 s start-up + 150 × 57 s = 8,723 s ≈ **2.4 h → 2.42 h × $0.80 ≈ $1.94.**
- **A100-large ($2.50/h): not measured.** I bounded the speedup between 2.6× (bf16 compute, 312 vs 121 TFLOPS: the training passes) and 6.7× (memory bandwidth, about 2.0 vs 0.3 TB/s: decode). That gives 8.5–22 s per step, so 173 s + 150 × (8.5 to 22 s) ≈ **24–58 min → $1.01–$2.40.** On cost, A100 is roughly the same as L4; it buys wall time, not dollars. One 2-step run on A100 (about $0.15) would settle the range.
- **Caveats:**
  - If the chat-template fix makes completions stop early, steps get shorter.
  - A longer chat prompt (~385 tokens instead of 18) adds prefill and training tokens.
  - Checkpoint saves would add a little.

## Files

- `jobs/grpo_smoke.py`: training script (AlignTune `create_rl_trainer` + logging callbacks + weight-0 true-test reward)
- `jobs/run_smoke.sh`: container entry point (install + run)
- `jobs/requirements-lock.txt`: exact environment (frozen from the local WSL venv, minus aligntune)
- `jobs/grader.py`: copy of `baseline/grader.py`
- `jobs/runs/{dry1,dry2,smoke10,smoke10-topp1}/`: job logs, per-step metrics, step timings, true-test groups, resolved GRPO args

**Exact commands**, run from `<repo>` with the Windows `hf` CLI 1.24 logged in as ebt005:

```
hf buckets create ebt005/p9-grpo-smoke --private
hf buckets sync .\jobs hf://buckets/ebt005/p9-grpo-smoke/jobs
hf jobs run --flavor l4x1 --timeout 25m --secrets HF_TOKEN -v hf://buckets/ebt005/p9-grpo-smoke:/out --name p9-grpo-smoke10 -d ghcr.io/astral-sh/uv:python3.12-bookworm bash /out/jobs/run_smoke.sh 10 smoke10
hf jobs run --flavor l4x1 --timeout 25m --secrets HF_TOKEN -v hf://buckets/ebt005/p9-grpo-smoke:/out --name p9-grpo-smoke10-topp1 -d ghcr.io/astral-sh/uv:python3.12-bookworm bash /out/jobs/run_smoke.sh 10 smoke10-topp1 --top-p 1.0
```

The dry runs used the same command with `2 dry1` / `2 dry2`. Nothing was pushed to any repo. The bucket is private and the token never appears in any log (checked by grep).
